## Project Overview

HenWen is a browser-based AllStarLink 3 node manager and kiosk display. It runs as a systemd service (`HenWen`) on the same Debian machine as Asterisk, installed to `/opt/HenWen`.

- **Author callsign:** N8GMZ
- **Club callsign:** WE8CHZ (do not use for author attribution)

## Hardware target

**Minimum supported hardware is a Raspberry Pi Zero 2 W** (quad-core Cortex-A53 @ 1GHz, has NEON) — **except for the stream relay's YouTube video target**, which is carved out as a known exception (see below). All new code — especially anything CPU-heavy like ffmpeg pipelines, background threads, or per-request work — must be written with the Pi Zero 2 W ceiling in mind, not just whatever the current dev/deploy box happens to be. When adding or changing something with real CPU cost, flag explicitly whether it's likely to run acceptably on a Pi Zero 2 W, the same way you'd flag a breaking API change. The *original* Pi Zero/Zero W (single-core ARM11, no NEON) is not a target for anything — its lack of NEON makes real-time libx264 encoding infeasible regardless of tuning, so there's no reasonable amount of optimization that reaches it.

**Exception — YouTube streaming:** the stream relay's YouTube video encode (waveform + background + text overlay, libx264 `ultrafast` CBR at 1280x720@25fps) was tuned and benchmarked against a desktop-class x86 core (Intel i5-8500T), not a Pi Zero 2 W, and is not held to the Pi Zero 2 W floor. Rough estimate (Cortex-A53 vs. that core's published single-thread benchmarks, not measured on real Pi hardware): the video encode alone could need on the order of 400%+ of a single A53 core, i.e. most of the chip's 4 cores just for that one ffmpeg process, competing with Asterisk, gunicorn, the AMI poller, and Broadcastify's own (much cheaper, audio-only) encode — not validated on real Pi Zero 2 W hardware, but treated as a real risk rather than assumed fine. A Raspberry Pi 4 (4GB+) or better is the reasoned (also not hardware-measured) recommendation for anyone actually wanting to use the YouTube target; this is surfaced to the owner as a warning on the Manager > Stream Relay page next to the YouTube fields, not just documented here. The Broadcastify target (audio-only, no video encode) is not part of this exception and stays held to the Pi Zero 2 W floor like everything else.

## Running and Deploying

There is no build step. The app runs directly via gunicorn.

**Deploy changes to the live service:**
```bash
sudo cp -r app.py audio_relay.py recording.py stream_relay.py templates static /opt/HenWen/
sudo systemctl restart HenWen
```

**View live logs:**
```bash
journalctl -u HenWen -f
```

**Run directly (dev/debug, not via gunicorn):**
```bash
cd /opt/HenWen
./venv/bin/python3 app.py
```

**Install/reinstall:**
```bash
sudo bash install.sh   # copies files to /opt/HenWen, installs venv, enables service
```

There is no linter configuration. Unit tests exist under `tests/` — see **Testing** below.

## Testing

`tests/` holds pytest-based unit/regression tests for the pure logic in `app.py` (rpt.conf parsing/validation, NWS alert helpers, connector scheduling, active-session tracking) plus a handful of Flask-test-client route smoke tests (login/setup flow, session, role gating). There's no coverage of the AMI client, audio pipeline, or background poll loops themselves — those need a live Asterisk/AMI to exercise meaningfully.

**Setup (one-time):**
```bash
python3 -m venv venv   # or reuse /opt/HenWen/venv if this checkout *is* the live install
./venv/bin/pip install -r requirements.txt -r requirements-dev.txt
```

**Run:**
```bash
./venv/bin/pytest
```

`tests/conftest.py` sets `HENWEN_SKIP_STARTUP=1` (and points `DB_PATH`/`RPT_CONF_PATH`/`SOUNDS_DIR`/etc. at a temp dir) *before* importing `app.py` — that env var is the only test-specific seam in `app.py` itself: it skips the unconditional module-load startup block (AMI poller, favstats/NWS/release pollers, `load_astdb()`, ...) described below, since none of that should run — or touch real `/etc/asterisk` paths — just because the module got imported by pytest. It's a no-op in every other context (gunicorn, `python3 app.py`), so production startup is unchanged. Each test that touches the DB gets its own fresh sqlite file via the `fresh_db`/`client` fixtures — see conftest.py for how (`DB_PATH` and the `_db_ready` schema-init flag both get monkeypatched per-test, since `get_db()` only runs its schema/migration statements once per process by design).

## Architecture

### Single-file backend

`app.py` (~7800 lines) contains everything: Flask routes, AMI client, rpt.conf parser, SQLite schema, and all background threads. There is no module split.

### Background threads (started at module load, bottom of app.py)

Daemon threads launch when gunicorn imports the module:
- `start_poller()` — AMI poll loop (1s interval): refreshes node keyed/connected state from Asterisk into an in-process cache
- `start_favstats_poller()` — polls AllStarLink stats API (30s interval) for favorite node status
- `start_global_activity_poller()` — fetches global ASL activity feed for the kiosk map
- `start_announcer()` — fires scheduled audio announcements via AMI `rpt localplay`/`playback` (30s interval, `_run_due_announcements()`); covers upload, TTS, and NWS-sourced announcements identically
- `start_connector_scheduler()` — manages Smart Connector link/unlink on schedule
- `start_id_monitor()` — monitors node activity to trigger FCC ID audio playback
- `start_nws_alert_poller()` — polls api.weather.gov for active severe weather alerts (~120s interval, exponential backoff) and manages the lifecycle of auto-created NWS announcement rows; never triggers playback itself, that's still `start_announcer()`'s job
- `start_release_poller()` — checks GitHub for the latest published HenWen release once a day into an in-process cache (`get_latest_release()`); `/api/update-check` reads that cache instead of hitting GitHub live, and the Manager dashboard surfaces it as a dismissible bar to superusers only (checked once per login/page-load, via `checkForUpdate()` in `henwen-manager.html`)
- `start_aprs_poller()` — optional; maintains one persistent APRS-IS connection (via the `aprslib` pip package) filtered to `APRS_MAX_RADIUS_MI` around the node's own geocoded location, caching station positions in-process (`_aprs_cache`); no-ops with a log line until an admin saves a login callsign in Manager > Kiosk Settings, or if `aprslib` isn't installed. See "APRS-IS map layer" below.
- `start_iss_poller()` — fetches the ISS's TLE from SatNOGS DB every `ISS_TLE_POLL_SEC` (6h) into `_iss_tle_cache`, exposed via public `GET /api/iss/tle`; all position/pass propagation happens client-side. See "ISS tracking (map layer)" below.
- `start_meshtastic_poller()` — maintains one persistent connection to the public `mqtt.meshtastic.org` broker, subscribed to the owner's configured root topic/channel, caching decoded text messages in-process (`_meshtastic_cache`), mirrored to the `meshtastic_messages` table so a restart reseeds the cache instead of blanking it; re-reads `meshtastic_config` on every reconnect cycle the same way `start_aprs_poller()` does. See "Meshtastic MQTT panel" below.
- `start_recording_janitor()` — sweeps `recordings` every 5 minutes for age-based retention and global/per-user storage-cap enforcement, deleting the oldest rows/files first; never touches an in-progress recording. See "Audio recording and stream relay" below.
- `start_stream_relay()` — optional; maintains the persistent Broadcastify/YouTube Live relay when the owner has enabled at least one target, re-reading `stream_relay_config` on every reconnect cycle the same way `start_aprs_poller()` does. See "Audio recording and stream relay" below.
- `start_discord_relay_worker()` — drains a bounded queue of kiosk chat messages (`_discord_relay_queue`, filled by `api_chat_messages_post()`) and POSTs each to a Discord Incoming Webhook when the owner has one configured and enabled; not poll-based like the others, since there's nothing to poll — it just blocks on the queue between chat messages. See "Discord chat relay" below.
- `start_irc_relay()` — optional; maintains one persistent two-way IRC connection (`irc_relay.py`'s `IRCClient`) when the owner has enabled and configured it, re-reading `irc_relay_config` on every reconnect cycle the same way `start_aprs_poller()` does, plus a second dedicated thread draining the outbound `_irc_relay_queue`. See "IRC chat relay" below.

Because gunicorn runs `--workers 1 --threads 8`, all threads share a single process and in-process cache. Do not increase worker count without rethinking the AMI connection pool.

### Self-update

The update bar's "Launch Updater" button (`/api/update/launch`, superuser only) runs `update.sh` — but not as a direct child process. It's launched via `sudo systemd-run --unit=henwen-updater --collect update.sh` specifically so the script runs as its own transient systemd unit, outside HenWen.service's cgroup: the script ends by running `systemctl restart HenWen`, which would kill a plain subprocess child of the very process it's restarting. `update.sh` fetches `main` over plain HTTPS from the public repo (not the SSH `origin` remote — root may have no SSH key/agent under systemd-run), hard-resets to it, reinstalls `requirements.txt`, byte-compiles `app.py` as a sanity check before touching the running service (rolling back and aborting the restart if that fails), then restarts. This only works when `/opt/HenWen` is itself a git checkout of the repo — true of this specific deployment, but not of installs that used `install.sh`'s plain `cp -r` (which doesn't set up git at all). The required sudoers line is installed by `install.sh` alongside the existing restart/reload rules.

### AMI connection

`AMIClient` (class in app.py ~line 915) is a raw TCP socket client to Asterisk Manager Interface on port 5038. It is a persistent connection managed by `_poll_loop`. Routes read from the AMI cache (`get_cached_status()`) rather than issuing live AMI commands — this makes most status reads sub-millisecond. Commands that must be sent live (connect/disconnect, restart, etc.) use `ami_send_command()`.

### Smart Connector

`connectors` rows (`_run_connectors()`/`_connector_loop()`, 15s interval) each define a scheduled `local_node → target_node` link: on its configured schedule, the connector waits for `local_node` to go idle, connects to `target_node` (`ilink 3`), monitors activity through a settle window, then auto-disconnects after `idle_limit_sec` of silence. `disconnect_all_first` optionally drops whatever else is linked to `local_node` before making the new connection, with a second flag, `disconnect_skip_permanent`, choosing between two ways `_connector_do_connect()` (app.py) does that:

- **`disconnect_skip_permanent=1`** ("preserve permanent nodes"): only non-permanent peers are dropped, via a per-peer `ilink 11` on everything in the AMI cache's connected list *except* whatever this app's own `_kiosk_temp_conns` has recorded as permanent (set only when a user explicitly checked "Permanent" at connect time via the Status Board).
- **`disconnect_skip_permanent=0`** ("disconnect everything"): every currently-connected peer is dropped via per-peer `ilink 11`, unconditionally.

Both branches use `ilink 11`, never a bare `ilink 6`. `ilink 6` ("disconnect all") was the original implementation of the second case, but — like `ilink 1` (see `_connector_do_disconnect`'s docstring) — it does not reliably drop a link app_rpt considers permanent (one established via a static `rpt.conf` `connect=` stanza, or made permanent outside this app's own tracking, e.g. directly on the Asterisk CLI). Firing it and moving on left such a link connected with zero indication anywhere that the "disconnect all" had only partially worked — the per-peer `ilink 11` result is now checked and any failure logged as a `WARN`, since a bare `ilink 6`'s result was previously discarded outright. Confirmed as a live bug on a beta install (a permanently-connected favorite node stayed linked through a scheduled connector fire) before this was diagnosed by re-reading the code, since the specific node/connector involved didn't actually exist in that install's own `connectors` table — the surviving link was a manually-permanent Status Board connection, not a second Smart Connector.

The Manager UI's per-connector Delete button (and the same pattern on NWS Alerts, Announcements, and Node ID) builds its `onclick` handler as a single-quoted HTML attribute containing `JSON.stringify(name)`. `JSON.stringify` only escapes for a *double*-quoted JS-string context, so a name containing an apostrophe (e.g. "KE8WNV's Trivia Net") terminates the attribute early and silently breaks the click handler with no visible error. Fixed by wrapping the JSON payload in the existing `esc()` HTML-escaper before embedding it — any future button built this same way (id + JSON-encoded name in a single-quoted inline handler) needs the same wrapping.

### Database

SQLite at `/etc/asterisk/henwen.db`. Schema is defined inline in `get_db()` (called per request). Migrations happen via `ALTER TABLE` checks at startup — no migration framework. Tables: `users`, `favorites`, `settings`, `announcements`, `connectors`, `id_configs`, `permanent_links`, `alert_config`, `nws_alert_config`, `recording_config`, `stream_relay_config`, `meshtastic_config`, `meshtastic_messages`, `meshtastic_node_names`, `discord_relay_config`, `recordings`, and a connection history log table.

`announcements.source_type` distinguishes `'upload'` (user-uploaded audio file), `'tts'` (typed text, synthesized once at save time), and `'nws_alert'` (auto-created/retired by the NWS poller) — the scheduler (`_run_due_announcements()`) treats all three identically except for two NWS-only nullable columns: `max_defer_sec` (forces playback past a busy channel after being due too long; NULL preserves indefinite defer for every other row) and `nws_expires`/`external_id` (NWS lifecycle bookkeeping, unused by upload/tts rows).

### rpt.conf parsing

Custom parser (not `configparser`) — `_collect_stanzas()`, `parse_stanza_settings()`, `update_setting_in_content()`. It preserves comments and formatting on save and handles ASL3's multi-stanza structure (node stanzas, templates, macros, schedules).

### Audio streaming

Asterisk `MixMonitor` writes raw PCM to a FIFO (`/tmp/henwen_audio_<node>.sln`). `audio_relay.py` — a standalone process spawned by `_start_broadcast()` (~line 4710 in `app.py`), not a thread inside gunicorn — paces that PCM into strict 20ms frames (injecting silence when the node is quiet) and writes them to a second FIFO (`..._paced.sln`). ffmpeg reads that second FIFO directly and encodes WebM/Opus to its stdout. `_AudioBroadcast._read_loop` fans ffmpeg's stdout out to each client's `Queue` — not as raw bytes but parsed into WebM units (`_drain_webm`): the init segment is cached and replayed to every late-joining listener (a WebM stream is only decodable from its start; without this, a second listener's demuxer fails immediately) and everything after it is fanned out as whole ~200ms Clusters. `/api/audio/stream/<node>` streams from that queue to the browser.

The pacing loop runs in its own OS process specifically to avoid GIL contention: gunicorn's request handlers, the AMI poller, and other background threads sharing this worker's GIL can stall a real-time 20ms deadline long enough to be audible as a click or stutter. Running the frame loop in a separate process lets the kernel schedule it independently. The MSE live-edge controller in `status.html` keeps the browser at ~0.5s behind live edge using `playbackRate` adjustment, with a startup watchdog and stall-recovery rebuffer logic.

### Audio recording and stream relay

Two independent features, each its own standalone module (`recording.py`, `stream_relay.py`) — the project's `app.py`-single-file convention is deliberately broken here twice, once per feature, specifically so the two stay decoupled from each other and from `app.py`'s globals: neither module imports `app.py` or the other, and each is driven entirely by objects/callbacks app.py hands it (a WebM-chunk `.feed()` method, a logging callback, plain config values). If either file were deleted, the rest of the app — including the other one — keeps working unmodified. Both attach to a node's existing `_AudioBroadcast` the same way a browser listener does, via `add_client()`, so neither ever touches `audio_relay.py` or the raw-PCM FIFO plumbing.

**In-browser recording** (`recording.py`, routes in `app.py`) — a Record button next to Listen on the Status Board, visible only to accounts the owner has flagged `users.can_record` (a real per-user flag checked for every role including owner, not a role-implied capability). `POST /api/recording/start` holds its HTTP connection open for the recording's whole duration, mirroring `/api/audio/stream/<node>`'s own connection-is-the-lifecycle pattern: closing the browser tab raises `GeneratorExit`, which stops the recorder and finalizes its `recordings` row — there is no "resume after the tab closed" path. The `Recorder` pipeline is decode ffmpeg (WebM/Opus → raw PCM) → `SilenceGate` (trims continuous dead air down to a configured ceiling, not to zero, so a natural pause survives) → a periodic wall-clock-timed TTS timestamp splice (`_synthesize_timestamp_pcm()` reuses the existing Piper `_synthesize_tts()` call, cached per-minute so simultaneous recordings don't each shell out to Piper at the same tick) → encode ffmpeg → file under `RECORDINGS_DIR`. Storage is capped both globally and per-user (checked before a recording starts, then swept every 5 minutes by `start_recording_janitor()` alongside age-based retention — both cap/retention selection rules are pure functions in `recording.py`, testable without a DB or filesystem) and a single recording auto-stops at `max_recording_min`. On stop, the browser is handed a download URL (`GET /api/recording/<id>/download`) which it turns into an automatic save-to-disk; the file also stays server-side under retention, browsable/deletable (admin+) from the Manager "Recordings" page. A plain `user`-role recordist can't reach that page, since `/henwen-manager` itself is admin+ gated — instead, the Status Board's "My Recordings" button (next to Record, same `can_record`-gated visibility) opens a popup backed by the same `GET /api/recordings` list, scoped to the caller's own username, with self-service rename (`POST /api/recordings/<id>/rename`, sets the `recordings.label` column shown in place of the raw node/timestamp) and delete (`DELETE /api/recordings/<id>`) — both routes accept either the recording's own user or admin+, checked against `recordings.username`, matching the existing download route's ownership rule. Admin+ can do all three from Manager's Recordings page too, against any recording.

**Persistent stream relay** (`stream_relay.py`, poller + routes in `app.py`) — an owner-only, always-on relay of one node's live audio to Broadcastify (Icecast source client) and/or YouTube Live (plain RTMP push, no OAuth/Data API), entirely independent of any recording session or browser tab: `start_stream_relay()`'s `_stream_relay_loop()` re-reads `stream_relay_config` at the top of every reconnect cycle exactly like `start_aprs_poller()` does, so a saved config change or a disable toggle takes effect on the next natural reconnect without a HenWen restart, and no-ops until the owner has enabled at least one target. A `Relay` decodes the node's WebM/Opus once and fans the raw PCM out unmodified — no silence-trim or TTS splice, since a live stream should track real time — to independent `RelayTarget` processes, one per enabled destination, so one target's ffmpeg dying or reconnecting never touches the other or the decode stage. YouTube's RTMP push always includes a static dummy video track (`color=size=320x240`) alongside the real audio, since audio-only RTMP acceptance by YouTube's ingest wasn't something available to verify against a real account. `GET /api/stream-relay/status` (owner-only) exposes live per-target connected/disconnected state, polled by the Manager "Stream Relay" page while it's open.

Both modules' config lives in their own singleton table (`recording_config`, `stream_relay_config`) — deliberately not shared, even though both are owner-only settings — and both were verified end-to-end against real local infrastructure standing in for what they ultimately talk to: `recording.py`'s pipeline against real ffmpeg with synthetic and (for the TTS splice) the box's actual cached Piper voice model; `stream_relay.py`'s Broadcastify path against a real local Icecast instance (Broadcastify's ingest is Icecast-compatible) and its YouTube path against an ffmpeg-as-RTMP-server loopback. Real Broadcastify/YouTube accounts remain a manual verification step.

### Text-to-speech (TTS) Announcements

Piper (`piper-tts` pip package, shelled out to via `PIPER_BIN` — never `import piper`, so a missing dependency fails cleanly at TTS-use time rather than crashing the whole app at startup) synthesizes typed text to a WAV, which then goes through the same `_convert_to_ulaw()` ffmpeg pipeline uploaded files use — TTS and upload rows produce byte-identical output formats and share every downstream code path. Voice models (`TTS_VOICES`, a fixed curated dict, never an open picker) live in `TTS_VOICES_DIR` (default `/var/lib/asterisk/henwen_tts_voices` — **not** under `/opt/HenWen`, which is `root:root` and unwritable by the `asterisk` user the service runs as), downloaded on demand from Hugging Face's `rhasspy/piper-voices` repo and cached thereafter. Editing a TTS announcement's text re-synthesizes to a temp file and `os.replace()`s it atomically over the existing slug path — the slug/filename never changes on edit, so this is old-content/new-content at the same path, never a window where the scheduler could hit a missing file.

### NWS severe weather alerts

`_nws_alert_poll_loop()` polls `api.weather.gov/alerts/active?zone=<UGC>` for a single configured county/zone (`nws_alert_config`, a singleton table like `alert_config`) and manages the lifecycle of `announcements` rows with `source_type='nws_alert'` — it never plays anything itself, `_run_due_announcements()` does that on its own schedule exactly as it would for any other announcement. Two independent prune paths: on a successful fetch, anything no longer in the active set gets deleted; regardless of fetch success, anything whose own `expires` is more than 30 minutes past gets deleted too (a local, network-independent ceiling so a stale alert can't replay forever during a sustained NWS outage — the fail-safe stance is "don't assume an alert ended just because NWS is unreachable," but that can't be unbounded).

Dedup/lifecycle tracking (`announcements.external_id`) uses a **parsed VTEC identity** (`{office}.{phenomena}.{significance}.{ETN}`, e.g. `KMKX.TO.W.0075`), not NWS's CAP `id` field — verified against live data that the CAP `id` changes on every `messageType: Update`, so using it directly would delete-and-recreate the row (resetting `last_played`) on every routine update to a tracked storm instead of holding the intended replay interval. The VTEC string itself also embeds a timestamp range that must be excluded from the key, since a time-extension update changes it.

Spoken text is templated (`_nws_alert_spoken_text()`), not NWS's raw headline — see the function for the exact phrasing rules (state names dropped, natural "A, B, and C" county joining, on-the-hour times drop `:00`).

**Kiosk map highlight layer**: an "Alerts" checkbox next to Radar on the kiosk Map overlays the county/zone area(s) each active alert covers, as translucent polygons colored by severity (reusing the ticker's own `--danger`/`--warn` warning-vs-watch split). `_nws_resolve_alert_geometry()` (called only when `display_enabled`, alongside building `_nws_display_cache`) prefers the alert's own CAP `geometry` field when NWS includes one (most polygon-based Warnings, e.g. Tornado/Severe Thunderstorm) and otherwise falls back to resolving each of the alert's `geocode.UGC` codes to its zone/county boundary via `_nws_lookup_zone_geometry()` (the same `/zones/{county|forecast}/{code}` endpoint `_nws_lookup_zone_name()` already calls, but reading `geometry` instead of `name`) — cached indefinitely in `_nws_zone_geometry_cache` keyed by UGC code, since boundaries are static and this is now consulted every poll cycle rather than once per admin click. The resolved GeoJSON geometry rides along on the existing `GET /api/status/nws-alerts` payload (no new route), and the frontend (`status.html`) draws it with `L.geoJSON()` off the same 60s `refreshNwsAlerts()` cycle the ticker bar already runs on — the checkbox only gates whether `renderNwsAlertAreas()` draws anything, mirroring the ASL-activity toggle's "no separate fetch, just gate rendering of data already being fetched" pattern rather than APRS/ISS's own enable-side fetch.

### APRS-IS map layer

Optional "APRS" toggle on the kiosk's Map, next to the existing Radar checkbox. `start_aprs_poller()` opens one persistent connection to APRS-IS (`aprslib.IS`, receive-only login with passcode `-1` — this app only ever consumes the feed, never transmits) filtered server-side to `APRS_MAX_RADIUS_MI` (200mi) around the node's own geocoded rpt.conf location, and caches every position packet it sees in `_aprs_cache` (`{callsign: {lat, lon, symbol, comment, ts}}`, keyed by callsign so the latest report replaces the last). `GET /api/aprs/stations?radius=<1-200>` (public, same as the rest of the board's map data) filters that one shared cache by haversine distance per request — so however many kiosk viewers pick however many different radii, it still costs exactly one upstream APRS-IS connection, same "one shared in-process cache, many cheap reads" shape as the AMI/favstats/global-activity pollers. Entries older than `APRS_STALE_SEC` (2h) are pruned locally regardless of connection state, mirroring the NWS poller's local staleness ceiling.

The login callsign (`aprs_is_callsign`) is a Manager > Kiosk Settings field (`/api/kiosk/settings`, same route as idle timeout/clock format/timezone/map pin duration), not an env var — every operator using this feature must be a licensed amateur identifying with their own callsign, so each install's admin fills it in rather than the code defaulting to anything. `_aprs_poll_loop()` re-reads that setting at the top of every reconnect cycle rather than once at startup, so a saved change takes effect on the connection's next natural reconnect (or immediately after a HenWen restart) without needing one — `immortal=False` on the `aprslib` consumer call is what makes drops come back around to that check instead of aprslib reconnecting silently forever with the old identity. The value is validated server-side against `APRS_CALLSIGN_RE` (letters/digits, optional `-SSID`) before being saved or used, since it gets embedded directly in the raw APRS-IS login line. The feature no-ops (log line, not a crash) if no callsign is saved yet or the `aprslib` pip package isn't installed — same "fails cleanly at use-time" posture as Piper TTS.

The frontend's radius slider (1-200mi, default 25) and on/off state are plain `localStorage` prefs, same pattern as the Radar/tile-style toggles; a thin circle outline on the map traces the selected radius around the resolved center. Markers render as a small purple circle (`makeAprsIcon()`), deliberately not the teardrop node-pin or gold hosted-node star, fading with age the same way the global-activity pins do (`aprsPinStyle()`, mirroring `globalPinStyle()`), and live in their own `_aprsMarkers` array on a separate 5-minute poll timer (`APRS_POLL_MS`) so they're untouched by `updateMap()`'s much more frequent node/activity marker rebuild.

### Templates

- `templates/status.html` — kiosk/status board (`/` and `/status` routes); self-contained SPA with embedded JS (~1800 lines). Contains the live audio player, network map, weather bar, and global activity feed. Accessible without login.
- `templates/henwen-manager.html` — all manager pages (settings, connectors, user management, announcements, node ID, etc.) loaded as a SPA shell via `/henwen-manager`.
- `templates/login.html` — login and first-run account creation.

### Configuration

All config comes from environment variables set in `/etc/systemd/system/HenWen.service`. The service file is the single source of truth for AMI credentials, `SECRET_KEY`, paths, and tuning parameters. After editing the service file: `sudo systemctl daemon-reload && sudo systemctl restart HenWen`.

Key env vars: `AMI_USER`, `AMI_SECRET`, `SECRET_KEY`, `DB_PATH`, `SOUNDS_DIR`, `LOG_LEVEL` (`INFO`/`DEBUG`), `RPT_CONF_PATH`, `TTS_VOICES_DIR`, `PIPER_BIN`, `APRS_IS_PASSCODE` (default `-1`, receive-only), `APRS_IS_HOST`/`APRS_IS_PORT` (default `rotate.aprs2.net:14580`), `PASSWORD_PEPPER` (optional, empty/off by default — see "Auth and security"). The APRS-IS login callsign itself is a Kiosk Setting, not an env var — see "APRS-IS map layer".

### Auth and security

Flask-WTF CSRF on all mutating routes. Flask-Limiter on login. Three roles: Superuser (full access + raw rpt.conf editor), Admin (full access minus raw editor), User/Kiosk (connect/disconnect only). Role is stored in the SQLite `users` table and checked by `check_auth()` decorator.

Sessions are plain signed cookies — there is no server-side session store. To show a live "logged in users" count on the Status Board footer, `check_auth()` stamps each session with a random `sid` and touches an in-process dict (`_active_sessions`, guarded by `_active_sessions_lock`) on every authenticated request; `get_active_user_count()` prunes entries idle more than `ACTIVE_SESSION_WINDOW` (90s) and is called from `/api/status/board`. This state is per-worker-process — fine today since gunicorn runs `--workers 1`, but would need to move to the DB or a shared store if worker count is ever increased.

**Password hashing**: werkzeug's `generate_password_hash`/`check_password_hash` (scrypt, salted per-hash). An optional `PASSWORD_PEPPER` env var (empty/off by default) is mixed in via `_peppered()` before hashing — deliberately its own secret rather than reusing `SECRET_KEY`, since `SECRET_KEY` has a one-click rotation path in Manager > Settings that would otherwise silently break every stored password hash. `_verify_and_upgrade_password()` transparently re-hashes a pre-pepper account's hash the first time it logs in successfully after `PASSWORD_PEPPER` is set, so turning the pepper on doesn't require a bulk migration or lock anyone out.

**Login hardening** (`_do_login_attempt()`, shared by `login()` and `api_login()`): a fixed dummy hash (`_DUMMY_PASSWORD_HASH`, computed once at import) is run through `check_password_hash()` on every "unknown username" and "account locked" path so those can't be timing-distinguished from "known username, wrong password" — skipping the scrypt verification entirely for an unknown username is a measurable, exploitable timing oracle for username enumeration otherwise. A soft per-account lockout (`failed_login_count`/`locked_until` columns, `LOGIN_LOCKOUT_*` constants) kicks in after 5 consecutive failures with a capped-exponential backoff (30s doubling to a 15-minute ceiling) — layered on top of, not instead of, the existing per-IP `Flask-Limiter` limits, which alone don't stop a distributed attack against one specific account. A locked account gets the exact same generic "Invalid username or password" response as a wrong password, not a distinct "account locked" message, so the lockout state itself can't become a second enumeration signal. Usernames are matched case-insensitively (`COLLATE NOCASE`) everywhere an account is looked up or created, with a manual pre-check before every `INSERT` (SQLite's `UNIQUE` constraint is case-sensitive) to stop "Bob" and "bob" from ever coexisting as two accounts.

**Session invalidation on password change**: since sessions are stateless signed cookies with no server-side store to revoke from, `users.password_epoch` (bumped on every password change — self-service, admin-forced, or a completed reset/invite) is embedded in the session at login and checked on every request in `check_auth()`; a mismatch force-logs-out that session. This is the only mechanism that can invalidate an already-open session elsewhere when an account's password changes. A password change made through the same session that made it refreshes `session['password_epoch']` in place so that request's own next call isn't the one that gets bounced.

**Password requirements** (`_validate_new_password()`, shared by every "set a new password" site — initial setup, admin-created/edited accounts, self-service change, reset, invite acceptance): 8–256 characters, plus a soft/fail-open check against HaveIBeenPwned's Pwned Passwords API via k-anonymity (`_is_password_breached()` — only the first 5 hex chars of the password's SHA-1 are ever sent, the full password/hash never leaves this server). "Soft/fail-open" is load-bearing: any network error or timeout (3s) just skips the check rather than blocking account creation, since an HIBP outage must never be able to lock someone out of setting a password.

**Two-factor authentication (TOTP)**: optional, self-service, available to every role (not just admin+) via Manager > Settings and the Status Board's "Account" popup (`openAccountModal()` in status.html) — the latter exists specifically because a plain `user`/kiosk account can't reach Manager at all, and needed *some* way to manage its own password/2FA, which it didn't have before this. `pyotp`/`qrcode` (guarded import, same "fails cleanly, not at module load" posture as Piper/aprslib) back enrollment (`/api/mfa/setup` → `/api/mfa/confirm`, QR rendered as inline SVG via `qrcode.image.svg.SvgPathImage` to avoid a Pillow dependency) and login verification (`login_2fa()`/`api_login_2fa()`, reached via `_start_mfa_pending()` after a correct password when `totp_enabled` is set — a short-lived, deliberately-still-anonymous `session['mfa_pending_uid']`, not a logged-in session). Ten single-use recovery codes (sha256-hashed at rest, same posture as reset/invite tokens) are minted on enrollment and shown exactly once — this app's offline analog of an email-based recovery link, since there's no email/SMS infra to send one automatically. Disabling 2FA or regenerating recovery codes both require re-entering the current password, so a stolen/XSS'd session cookie alone can't strip an account's second factor. Admin+ can force-reset (never view or set) another account's 2FA from Manager > Users, for a lost device with no recovery codes left — same "can't see the second factor, only force a redo" property this app already has for passwords via the reset/invite flows, and gated by the same role-rank rules as every other User Management action.

### ISS tracking (map layer)

Optional "ISS" toggle on the kiosk's Map, next to Radar/APRS, with a pass-count selector (1-6 upcoming passes). `start_iss_poller()` fetches the ISS's TLE from SatNOGS DB every `ISS_TLE_POLL_SEC` (6h) into `_iss_tle_cache`, exposed via public `GET /api/iss/tle`. That's the entire server-side role — unlike APRS/global-activity there's no per-viewer filtering of shared state to do, so all propagation happens client-side in `status.html` via `satellite.js` (SGP4): current position (updated every 5s), and upcoming visible-pass prediction (elevation ≥ `ISS_MIN_ELEV_DEG`, 10°) against the observer coordinates already on hand from the board refresh (`_hostedNodes[0]`, the same geocoded node location APRS/NWS use). Passes are found by a coarse forward time-scan for elevation-threshold crossings (`ISS_PASS_COARSE_STEP_SEC`), refined by bisection; that same coarse scan doubles as a continuous ground track from "now" through the end of the last selected pass (`_issTransitTrack`), drawn dim/muted, with each found pass's own arc resampled at `ISS_PASS_FINE_STEP_SEC` and drawn on top in a bright color (solid = nearest pass, dashed = later ones) so the line-of-sight portions stand out against the full orbital path instead of the path just stopping at the horizon. Both layers are split at the antimeridian (each point's longitude is independently normalized to ±180°) and drawn once per `MAP_WORLD_OFFSETS` entry so they stay visible across repeated map copies, same as every other map layer; they also share one Leaflet Canvas renderer rather than individual SVG paths, since the continuous track can run to several thousand points. Re-derived every `ISS_PASS_RECOMPUTE_MS` (5 min) to drop passes that already happened and roll the next one into view.

### Meshtastic MQTT panel

A Status Board dash-card (split off underneath Latest Activity, same "main panel + smaller companion panel" rhythm as Node/Recent-Connections and Favorites/Chat) showing text messages from one public Meshtastic MQTT channel — Meshtastic being an unrelated LoRa mesh-radio protocol/community, surfaced here purely as a live feed alongside the repeater's own activity, not integrated with AllStar in any way. `start_meshtastic_poller()` maintains one persistent connection to the public `mqtt.meshtastic.org` broker (host/port/credentials are fixed in code, not owner-configurable — see `MESHTASTIC_MQTT_HOST` etc. in app.py), subscribed to `<root_topic>/2/e/<channel_name>/#`, decoding each message via `meshtastic_mqtt.decode_service_envelope()` and caching only successfully-decoded `TEXT_MESSAGE_APP` packets (the bulk of real traffic — position/telemetry/nodeinfo beacons — is discarded at decode time, not filtered afterward) into a shared in-process ring buffer (`_meshtastic_cache`, 50 most recent), same "one shared cache, many cheap reads" shape as the APRS/global-activity pollers. `GET /api/meshtastic/messages` (public) serves that cache to the kiosk panel, polled every 20s.

`_meshtastic_cache` alone doesn't survive a HenWen restart (it's an in-process `deque`, wiped on process exit) — every decode also inserts into the `meshtastic_messages` table (pruned to the same `MESHTASTIC_CACHE_MAX` rows on each insert, so it's a restart-survival mirror of the cache, not a growing history log) and `start_meshtastic_poller()` reseeds `_meshtastic_cache` from that table once, before the poll loop starts, so a restart resumes the panel where it left off instead of showing empty until new traffic arrives.

Root topic, channel name, and PSK (pre-shared key, base64-encoded) are Owner-only settings (`meshtastic_config`, a singleton table like `stream_relay_config`), editable from Manager > Meshtastic and re-read by the poller on every reconnect cycle — a saved change takes effect on the next natural reconnect, mirroring `start_aprs_poller()`'s behavior, without a HenWen restart.

A second, fully independent Owner-only relay (`meshtastic_discord_relay_config`, its own singleton table/webhook — Manager > Meshtastic's "Discord Relay" card) mirrors decoded Meshtastic text messages out to a Discord channel via an Incoming Webhook, architecturally identical to the Chat panel's own Discord relay (bounded queue + one dedicated worker thread, `_meshtastic_discord_relay_queue`/`start_meshtastic_discord_relay_worker()`, both reusing `_post_json_with_dns_backstop()`) but deliberately *not* sharing the chat relay's webhook — a mesh-radio feed is a different audience/destination than repeater chat, unlike the NWS alert Discord toggle which intentionally reuses the chat relay's one. `_meshtastic_on_message()` enqueues directly (sender's friendly name if already known, else the raw node id) right after a decoded text message lands in `_meshtastic_cache`, rather than going through a Flask route the way chat messages do. The payload always sets `allowed_mentions: {"parse": []}` too, arguably more load-bearing here than for chat since this text comes from unauthenticated public mesh radios rather than logged-in HenWen users.

`meshtastic_mqtt.py` is a standalone module (no Flask/DB dependency, same independence story as `recording.py`/`stream_relay.py`) holding the AES key derivation, AES-CTR decryption, and protobuf decoding — every constant and byte layout in it (the default 16-byte AES-128 key, the single-byte PSK "preset" expansion rule, the CTR nonce's exact byte layout) was verified against `meshtastic/firmware` source rather than implemented from a general description of the protocol, since a wrong nonce or key byte silently produces garbage plaintext instead of a decode error. Channel-PSK encryption here is unauthenticated (no MAC/auth tag), so `decode_service_envelope()` also gates on the decrypted portnum being `TEXT_MESSAGE_APP` and the payload being strict-valid UTF-8 before surfacing anything — defense against a wrong key occasionally "succeeding" into nonsense bytes that would otherwise render as a fake chat message.

The protobuf schema (`meshtastic_proto/`) is a hand-trimmed subset of `meshtastic/protobufs`' `mesh.proto`/`mqtt.proto` — same field numbers/types as upstream (so it stays wire-compatible with real traffic) but only the handful of fields HenWen actually reads, instead of the full ~10-file dependency closure those two files pull in (config/device_ui/module_config/atak/etc., all irrelevant here). `portnums.proto` is vendored unmodified since it's small and has no imports. See `meshtastic_proto/__init__.py` for the recompile command if a future feature needs more fields.

Messages render with the sender's friendly name, not the raw `!xxxxxxxx` node id — a node periodically broadcasts its own name as a `NODEINFO_APP` packet on the same channel, decoded by `meshtastic_mqtt.decode_nodeinfo()` (added onto the `mesh_min.proto` `User` message: `short_name`/`long_name` only, same trimmed-schema approach as everything else here) and kept in `_meshtastic_names_cache`/the `meshtastic_node_names` table (one upserted row per node id, current state rather than history, mirroring `_meshtastic_cache`'s own `meshtastic_messages` restart-survival table) — see `_remember_meshtastic_node_name()`. `_meshtastic_on_message()` tries the nodeinfo decode first and returns immediately on a hit, since a given payload is never both a text message and a name announcement; `GET /api/meshtastic/messages` joins each cached message against the name cache at request time (not at decode time), so a name learned after a message already landed in the cache still backfills onto it on the client's next 20s poll. The raw node id is never dropped, only backgrounded — the kiosk panel keeps it in a hover title, since it's the one thing guaranteed unique per node when a name is missing, blank, or (rarely) reused.

### Discord chat relay

A one-way mirror of the kiosk Chat panel (see "Kiosk chat panel" above) out to a Discord channel, so people can follow the conversation without being logged into the board — nothing posted in Discord comes back into HenWen chat, and there's no bot/gateway connection, just a plain Discord Incoming Webhook POST. Config (`discord_relay_config`, a singleton table like `meshtastic_config`) is Owner-only (`enabled`, `webhook_url`), editable from Manager > Discord Relay; `webhook_url` is a real secret (anyone holding it can post into the linked channel), so unlike the Meshtastic PSK it's masked in the UI, and the save route rejects anything that isn't shaped like a `discord.com`/`discordapp.com` webhook URL.

`api_chat_messages_post()` enqueues `(username, message)` onto a bounded in-process queue (`_discord_relay_queue`, maxsize 50) right after the chat row is committed — never inline, since a Discord outage must never be visible to someone posting in kiosk chat. One dedicated daemon thread (`start_discord_relay_worker()`) drains that queue, re-reading `discord_relay_config` on every message (so a disable takes effect immediately for anything still queued) and POSTing via stdlib `urllib.request` (same DNS-timeout backstop as the favstats poller's `_fetch_node_stats()`, since `urlopen(timeout=...)` alone doesn't reliably bound DNS resolution). A full queue drops the newest message with a WARN log rather than blocking the chat POST or growing unbounded. On a failed POST (bad/revoked URL, Discord down), the worker logs a WARN and drops that one message — no inline retry, so one bad webhook can't stall the rest of the queue.

The payload always sets `"allowed_mentions": {"parse": []}` — the one real security property of this feature: without it, a kiosk user typing `@everyone` in chat would ping the entire linked Discord server through the webhook, since Discord's webhook `allowed_mentions` field overrides whatever's in the message content.

The `alert_config` push-notification system (below) also has its own Discord toggle, and reuses this same saved webhook URL rather than asking the owner to configure a second one — a HenWen install has exactly one Discord destination. Chat relay and alerts are otherwise unrelated: the chat relay is always-on (once enabled) and mirrors every message, where alerts are a `_send_alert()` fan-out that fires only on the specific conditions Manager > Alerts is configured for. `_post_json_with_dns_backstop()` (near `_send_alert()`) is the shared low-level poster both features' Discord path calls, so the DNS-timeout backstop only needs to exist once.

`ntfy`/Pushover/Discord/Kiosk Chat/IRC in `alert_config` are independent enable toggles (`ntfy_enabled`/`pushover_enabled`/`discord_enabled`/`chat_enabled`/`irc_enabled`), not a mutually-exclusive single `provider` select like the feature originally shipped with — `_send_alert()` fans an alert out to every enabled destination, each in its own try/except, so one failing (bad token, network hiccup) can't silently swallow the others. Existing installs upgrading from the single-`provider` schema are migrated once, automatically: the old `provider` column is left in the table (unused, harmless) and its value is copied into the matching new `_enabled` column the first time `get_db()` runs after upgrade.

The IRC destination (`irc_enabled`) sends straight to whatever `IRCClient` the IRC relay (see "IRC chat relay" below) currently has live, via `client.send_message()`, formatted as `[ALERT] <title>: <message>` — deliberately **not** through `_irc_relay_queue`, unlike a normal chat message: that queue's messages get the `<username> message` bracket format `api_chat_messages_post()` uses, which isn't right for a system alert, and an alert firing while the relay happens to be mid-reconnect should log a clear WARN saying so rather than silently vanishing into a dropped-on-full queue the same way an ordinary chat message would.

The Kiosk Chat destination (`chat_enabled`) posts the alert straight into `chat_messages` (`username='HenWen Alert'`, `role='system'`, `user_id=0` — a reserved sentinel below `chat_messages`'s real `AUTOINCREMENT` id range, since there's no FK constraint on that column to satisfy) rather than going through `api_chat_messages_post()`. That's deliberate, not a shortcut: that route also enqueues onto the Discord chat relay queue, which would double-post the alert to Discord whenever both `chat_enabled` and `discord_enabled` are on, since the Discord branch above already delivers it there directly. The kiosk Chat panel (`status.html`) gives `role==='system'` rows a distinct warning-colored left border/username so an alert doesn't read as just another user's chat line.

### IRC chat relay

A two-way bridge between the kiosk Chat panel and one IRC channel, via `irc_relay.py`'s hand-rolled `IRCClient` — unlike the Discord relay above, which is stuck one-way because a fire-and-forget Incoming Webhook has no inbound side, IRC is a real persistent bidirectional connection, so there's no reason to withhold relaying messages typed in the channel back into kiosk chat. Config (`irc_relay_config`, a singleton table like `discord_relay_config`) is Owner-only (`enabled`, `host`, `port`, `use_tls`, `channel`, `channel_key`, `nick`, `nickserv_password`), editable from Manager > IRC Relay. `nickserv_password` is a real secret but is stored and returned plaintext, matching `discord_relay_config.webhook_url`'s existing precedent — this app has no secrets-encryption layer to plug into.

`irc_relay.py` is a standalone module with no import-time dependency on Flask or the DB (same independence story as `recording.py`/`stream_relay.py`), and pulls in no new pip dependency: IRC's wire protocol is CRLF-terminated text lines under 512 bytes with a handful of numeric replies and PRIVMSG/PING/JOIN commands — simpler than the AMI protocol `AMIClient` already hand-rolls over a raw socket in this same codebase, and far simpler than the binary/framed protocols `aprslib`/`paho-mqtt` were pulled in for elsewhere. `IRCClient` itself is deliberately "dumb" — one `connect()` (NICK/USER registration, TLS via `ssl.create_default_context()` when `use_tls` is set), an optional `identify()` (plain in-band `PRIVMSG NickServ :IDENTIFY <password>`, not SASL — skipped entirely when no password is saved), `join()`, and a blocking `read_loop(on_message)` that answers PING with PONG and hands channel PRIVMSGs to a callback, returning (not raising) on any disconnect. It never requests the `echo-message` capability (no `CAP` negotiation at all), and additionally drops any PRIVMSG whose nick matches its own as a backstop against a network that echoes by default anyway — both exist purely to prevent a message HenWen just sent from looping back in as if it were a new inbound one.

Reconnect/backoff is deliberately **not** `irc_relay.py`'s job — app.py's `_irc_relay_loop()` owns that state machine, mirroring `_meshtastic_poll_loop()`'s shape exactly: re-reads `irc_relay_config` at the top of every reconnect cycle (so a saved channel/nick/host change takes effect on the next natural reconnect without a HenWen restart), no-ops until `enabled` plus host/channel/nick are all present, and backs off exponentially (capped) on repeated connection failures.

Outbound (kiosk chat → IRC): `api_chat_messages_post()` enqueues `(username, message)` onto `_irc_relay_queue` (bounded, maxsize 50) right alongside the existing `_discord_relay_queue` enqueue — same drop-newest-on-full, never-block-the-post semantics, for the same reason: an IRC outage must never be visible to someone typing in kiosk chat. A separate `start_irc_relay()`-spawned sender thread (`_irc_relay_send_worker()`) drains that queue onto whichever `IRCClient` is currently live, formatting each line as `<username> message text` (the classic relay-bot bracket convention) and dropping the message outright — not buffering it — if nothing is currently connected, matching the Discord relay's "an outage just means that message doesn't reach the other side" posture rather than adding queued-across-reconnects state.

Inbound (IRC → kiosk chat): `_irc_relay_on_message()` is handed to `IRCClient.read_loop()` as its callback and inserts straight into `chat_messages` with `role='irc'` and the same `user_id=0` sentinel the NWS/system alert path uses — deliberately bypassing `api_chat_messages_post()`, the same way system alerts do, so an inbound IRC message can never get re-enqueued onto `_irc_relay_queue` and echoed straight back out. The kiosk Chat panel (`status.html`) gives `role==='irc'` rows their own distinct left-border/username color (green, reusing the `--green` theme token already present in every palette) — a parallel treatment to, but visually distinct from, `role==='system'`'s existing warning-colored alert styling, since an inbound IRC message is a different kind of "not authored via the login-gated compose box" than a system alert.

A persistent raw-socket IRC connection is trivially fine on the Pi Zero 2 W floor (see "Hardware target" above): it's two mostly-idle threads (one blocked in `recv()` waiting for lines, one blocked on `queue.Queue.get()` pacing outbound sends at a flat 1 line/sec — a conservative rate, not tuned against any specific network's actual flood-control policy) with no subprocess and no audio/ffmpeg involvement — lighter than the AMI poller already running continuously on every install. TLS adds one-time handshake cost at connect/reconnect only, not sustained cost.

### Service identity

The systemd unit is `HenWen`, installed at `/opt/HenWen`. This was renamed from the project's original `ASL3-EZ` name (2026-07-03) — there was no install base yet at the time, so the rename covered the systemd unit, install path, sudoers rule, database path, sounds directory, TTS voice cache directory, and the `henwen/<slug>` AMI command prefix in one pass rather than leaving internal `asl3ez`-branded paths in place. If this project ever gets a real install base, do not repeat a path/unit-name rename casually — it requires a real migration script, not just an in-place edit, since existing installs would need `systemctl stop`, a data move, a new unit file, and an updated sudoers rule to not break.
